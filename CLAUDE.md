# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**OneFlowe** is a multi-tenant retail operations platform for Apricart. It has three distinct portals:
- **Super Admin portal** — global inventory, organizations, branches, and platform-level configuration
- **Organization/Branch portal** — day-to-day operations, budgets, orders, and inventory per org/branch
- **Order Portal** — employee-facing e-commerce interface for placing internal orders (`/shop`)

Two Vitest projects: `vitest.config.ts` (jsdom, tests beside the code) and
`vitest.integration.config.ts` (node, `tests/integration/**`, one file at a

## Architecture

### Tech Stack
- **Framework**: Next.js 15 App Router (TypeScript)
- **UI**: shadcn/ui (New York style) + Radix UI + Tailwind CSS 4
- **Database**: PostgreSQL via Drizzle ORM (schema at `db/schema.ts`, migrations in `drizzle/`)
- **Auth**: NextAuth.js credentials provider — encrypted JWT cookies backed by a per-browser revocation registry, with a 1-15-minute tenant idle timeout and fixed 8-hour absolute lifetime
- **Cache/MFA**: Redis via Upstash
- **Storage**: AWS S3
- **Email**: Nodemailer (SMTP)
- **Charts**: Recharts
- **PDF/Export**: jsPDF + xlsx

### Role-Based Routing

The request proxy (`proxy.ts`) enforces routing by role:
- `ORDER_PORTAL` users → only `/shop/*`
- All other roles → `/dashboard` and portal pages; redirected away from `/shop`
- Four roles: `SUPER_ADMIN`, `HEAD_OFFICE`, `BRANCH_ADMIN`, `ORDER_PORTAL`
- Granular permissions live in `rolePermissions` table, evaluated via `lib/permissions.ts`

## Important Patterns

- **API routes** follow the pattern `app/api/v1/<resource>/route.ts` and use `lib/error-handler.ts` for consistent error responses.
- **Server components vs client components**: API data fetching happens in client components via `lib/hooks/` and `lib/api.ts`; use `"use client"` at the top of interactive components.
- **Inventory cascade**: When inventory changes at the global level, `lib/inventory-cascade.ts` propagates changes down to org and branch levels. Always go through this utility rather than writing directly.
- **Pricing — resolving**: A product's price is layered — group override, then organization override, then global base price. Always resolve it through `lib/server/effective-price.ts` (`resolveEffectivePriceCents`, `effectivePriceCentsSql`, `scopedOverrideCentsSql`); never write a `customPrice ?? basePrice` expression by hand, or the price charged and the price displayed will drift. The group tier applies only where exactly one group is in scope (a branch, or an authorized group-portal submission).
- **Pricing — the downward rule**: A price change never reaches past a tier that has set its own price. Changing the global base price does **not** touch any organization or group price, whatever their values happen to be; changing an organization price does not touch the global one, and reaches groups only as the administrator chose; changing a group price touches nothing above it. `cascadeGlobalProductFieldUpdate` cascades descriptive fields only (`CASCADABLE_GLOBAL_FIELDS`) — never `basePrice`.
- **Pricing — propagating**: Changing an organization price moves every group that has no override of its own, because those groups inherit it. `lib/group-price-propagation.ts` turns an administrator's choice into a plan: `all` (clear group overrides so everyone follows), `selected` (the chosen groups follow; every other unpriced group is *pinned* at its current price so it does not drift), or `none` (the default and the pre-existing behaviour). The planner is pure and shared — the confirmation dialog previews with it and the server rebuilds the plan with it from rows read **before** the price update, inside the same transaction. Clients send a mode, never a plan.
- **Pricing — changing**: **Only `SUPER_ADMIN` may write a price, at any tier.** The rule lives in `lib/pricing-access.ts` (`canMutatePrices`, `priceMutationFailure`, `rejectPriceFieldsForRole`) and is carried in RBAC as `Permission.PRICING_MANAGE`, granted to Super Admin alone. Administering a catalogue, tenant, or group does not carry the right to change what anyone is charged — Head Office may read prices but never set them. Any new endpoint that writes a price column must go through that module and be added to the route list in `lib/pricing-access.test.ts`. Reading a price is a separate concern, governed by `lib/price-visibility.ts`.
- **Image storage**: Uploaded images live in S3, never in the database. `POST /api/v1/upload/image` sanitises through `sharp`, writes the object, and returns an application path (`/api/v1/images/products/<uuid>.<ext>`) which is what gets stored in `imageUrl`/`customImageUrl`. `GET /api/v1/images/*` streams it back to signed-in users; the bucket itself is private. Rows written before this change still hold `data:` URLs and still render — use `isDataUrl`/`isStoredImagePath` from `lib/server/image-storage.ts` to tell the two apart, and `npm run migrate:images-to-s3` to move the remainder. Never write a `data:` URL to a column.
- **Mirrored accounts and email login**: A user row with `external_source` set was mirrored from another system and **cannot sign in with an email address** — only with its username (`lib/auth-options.ts`, `loadStaffLoginRecord`). Such a person holds one account per role behind a single shared email (`<employee code>-ba` to approve, `-op` to order), so an email alone cannot say which portal they meant. Accounts created in the portal leave `external_source` null and keep email-or-username login. Never relax that guard to "fix" a login complaint from a K-Electric user; point them at their username.
- **Forced password change and the emailed proof**: every K-Electric account was flagged `must_change_password` on 2026-09-17; the flagged session is sent to `/change-password` and refused on every other `/api/v1/*` path (`lib/password-change-pending.ts`). The change itself (`lib/server/password-change.ts`) was gated on a `VERIFY_EMAIL` code entered on the same session. **That proof is switched off for now** by `PASSWORD_CHANGE_EMAIL_VERIFICATION` in `lib/password-change-policy.ts` — a constant in code, deliberately not an environment variable, read by the server module and the page alike (`plans/OF-KE-password-change-without-email-verification.md`). With it off, the change still requires the current password, the policy, new ≠ old, still clears the flag, bumps `session_version` and drops every session, and still has to find the token's own live `auth_sessions` row (only the freshness term goes); the audit row says `emailVerified: false`. To re-enable, set the constant back to `"required"` and update `lib/password-change-policy.test.ts`. The required path keeps running in `tests/integration/password-rotation.test.ts` (policy mocked on); the shipped path in `tests/integration/password-change-direct.test.ts`.
- **Self-service password reset** (`plans/OF-AUTH-self-service-password-reset.md`): `/forgot-password` → `POST /api/v1/auth/password-reset/{request,verify,complete}`, all public, logic in `lib/server/password-reset.ts`, state in `password_reset_challenges` (HMAC digests only, never the code or token; one live challenge per account by partial unique index). It follows login's identifier rules — a mirrored account resets by username, never by email, and an email naming more than one account resets nothing. **The request step must not reveal whether an account exists, by body or by timing**: every input gets a 202 and a challenge id (a random decoy for non-accounts), the email is sent via `after()` rather than before the response, and the response is held to `PASSWORD_RESET_REQUEST_MIN_RESPONSE_MS`. For the same reason the verify step never reports remaining attempts. Completion bumps `session_version`, revokes every `auth_sessions` row and clears `must_change_password` and the lockout. Both the Order Portal profile menu (`components/auth/order-portal-profile-menu.tsx`, used by `/shop` and the group storefront) and the admin topbar link to it. `tests/integration/password-reset.test.ts` carries the database behaviour.
- **Self-service joining is locked to the organization's email domain** (`plans/OF-JOIN-email-domain-lock.md`, building on `plans/OF-JOIN-organization-self-service-join.md`). Super Admin sets `organizations.email_domain` in Create/Edit Company; the join form fixes it as the address suffix, and `POST /api/v1/join/requests` refuses — before hashing or storing anything — an organization with no domain (409) or an address not at exactly that domain (400, no subdomains), judged against the domain re-read with the code on that request (`joinEmailDomainRefusal`), never one the page sends back. The lookup answers a domainless organization with `emailDomain: null` and no branches or groups, and the page shows a "contact your organization" prompt instead of the form. Every rule is in `lib/organization-email-domain.ts` and pinned by `organizations_email_domain_shape_ck`. **The column is deliberately not unique**: K-Electric and K-E-Demo share addresses and so share a domain — the join code selects the tenant, the domain only restricts what an applicant may type.
- **K-Electric legacy sync**: Reference data comes from the legacy platform via `npm run sync:ke` (organization, branches, groups, catalogue, users), and orders via `npm run import:ke-orders` — in that order, because an order cannot be written until its branch, ordering user **and products** exist. Both are dry-run by default and require the plan digest they print in order to commit. Planning logic is pure and lives in `lib/legacy-import/ke-sync.ts` and `lib/legacy-import/ke-products.ts`; branches are matched by `external_id`, never by name once pinned. Organization 2 (`K-E-Demo`) shares many of the same emails and must never be touched.
  - **The target organization is resolved by `--organization-code`, not compiled in** (default `0001`). Both scripts refuse if that code belongs to a differently-named tenant, and `sync-ke.ts` creates the organization only with `--create-organization`. This is what lets the whole sync be rehearsed on a test database, where `0001` is taken by another tenant. The two scripts must always be pointed at the same code or the orders land in a tenant the sync never populated.
  - **The sync creates catalogue entries and groups, and writes `base_price`.** It previously refused both because pricing is `SUPER_ADMIN`-only; the refusal was reversed because the order import rejects every line as `PRODUCT_NOT_FOUND` without them. It still never changes the price of a product that already exists — legacy prices per branch, OneFlowe has no per-branch tier, so a new product takes the price most of its branches agree on and every disagreement is reported, not applied. Groups are created with no price of their own.
  - **`normalizeProductName` in `lib/legacy-import/ke-electric.ts` is the single join key** between a legacy order line and the catalogue. `ke-products.ts` re-exports it rather than reimplementing it: a normaliser that merely looks equivalent splits one product into two, and the order line then matches both and is refused as `PRODUCT_AMBIGUOUS`.
  - **A first run against an empty database needs two passes.** People at a branch created in the same run are skipped as `BRANCH_NOT_PINNED`, because the branch did not exist when the plan was built. Re-run and they are picked up; a third run reports nothing to do. Branch budgets follow the same rule, for the same reason.
  - **Branch budgets come from the location rows, not a separate endpoint** (`lib/legacy-import/ke-budgets.ts`). `MonthlyBudget` is the allocation; `TotalBudget` is what is **left**, not what was granted — KE HOUSE carries MonthlyBudget 900,000 against TotalBudget 6. It is never written as an allocation, but it is exactly OneFlowe's `allocated + credited − spent − held` (verified to the rupee across every funded branch), so for a location whose `MonthlyBudget` is 0 yet still has money left (HSEQ: 0 / 5) the allocation is `TotalBudget + our used`. **Legacy is authoritative for the current month's allocation**: a missing row is created, a lower one is raised (always safe under `budgets_values_valid_ck`), a higher one is lowered only with `--lower-budgets` and only if the invariant still holds — otherwise it is reported as drift. A location legacy leaves at 0/0 gets no row of its own (the shop creates one at zero on demand) but a row we already hold for it is compared like any other. The API exposes only the current tenure; historical months still come from the report file via `scripts/import-ke-branch-budgets.ts`. Spend stays the job of `backfill-ke-budget-spend.ts` — and a branch showing exactly 0 remaining is usually a row that backfill created at `allocated = spent + held` before the sync could set the real figure. That is the default mode, `--budgets=legacy`. **`--budgets=zero` is the other one** (`planZeroBudgets`): every active branch's allocation for the month goes to the floor `budgets_values_valid_ck` allows (`spent + held − credited`, so nothing remains to order against), a missing row is created at 0, and **`branches.baseline_budget_cents` is cleared** — two paths in `app/api/v1/budgets/route.ts` re-fund from it (a missing month row is created at the baseline; a zero row with no spend is treated as stale and reset to it), so a zero that keeps the baseline is undone by the next page load. Legacy figures are ignored for that run. `--budgets=skip` leaves budgets alone. Choose the mode deliberately on every run: the default would raise a zeroed month straight back to the legacy figure. **A committed zero run is reversed by `npm run restore:ke-zeroed-budgets`** (`lib/legacy-import/ke-budget-restore.ts`), from the before-values in that run's own commit report — not from legacy, whose figures differ from OneFlowe's on a few locations. It raises each lowered allocation back only if the row still holds what the zero run wrote, puts each cleared baseline back only if it is still 0 (that is what switches the monthly re-allocation on again — no code condition was ever changed), leaves the rows the zero run created at 0 alone, and reports anything that moved since rather than overwriting it. Dry-run and digest-gated like the sync.
  - **Which branch sees which product is the legacy per-location item list, and the sync mirrors it** (`lib/legacy-import/ke-branch-catalogue.ts`). Legacy keeps one item row per product per location (`Item.CategoryID -> Category.LocationID`); a Distribution-group location carries ~63 items, an Enabling-group one ~120. The shop lists a product only when its `branch_inventory` row is visible **and** active, its `organization_inventory` row is active, its `global_products` row is active, and `stock_quantity` covers the order — so the sync does all four: it wakes a global product the KE import parked `inactive` (only one it created — `metadata.legacySource = KE_LOGISTICS` or a `KE-` code; anything another hand retired stays retired), activates the organization entry, gives every product legacy sells `--stock` units (default 500; legacy tracks no stock, OneFlowe decrements it on every order) — a zero-stock product on every run, and every product only with `--reset-stock`, so a figure an administrator typed or orders wore down is not clobbered by a routine sync — and upserts the branch row. It never hides: a product visible at a branch that legacy does not list there is reported as an extra. The Head Office "assign" endpoint skips any existing non-deleted row, visible or not, which is why a dormant row from the legacy order import cannot be surfaced through the UI. Products created in the same run are assigned on the next — the same two-pass rule as branches and people.
  - **`import:ke-orders` defaults to the whole history** and fetches the order list **one calendar month at a time** (`monthWindows`). A single request for twenty months returns ~1MB and the legacy platform answers by throttling or dropping the connection. Detail fetches run at concurrency 3, and 403/429/503 back off exponentially in seconds — sub-second retries just burn the attempt budget and kill the run.
  - **A person's branch comes from `SubuserLocations`, never from `LocationID`** (`legacyLocationOf` in `ke-sync.ts`). `LocationID` looks authoritative and is not — legacy populates it for everyone, overwhelmingly with 2 (KE HOUSE). For 13 of the 148 people the two disagree, and trusting `LocationID` parked all 13 at KE HOUSE, left branches such as GSMP-KKI with no staff at all, and made their orders unattributable. `LocationID` is honoured only when `SubuserLocations` agrees the person is there. The sync also *moves* an existing account that is on the wrong branch (`branchMoves`), because the assignment is legacy's to state, not ours.
  - **An imported order's branch comes from the legacy `LocationID`, never from the location name** (`lib/legacy-import/ke-order-branches.ts`, used by `import-ke-orders.ts`). Legacy has twins whose names differ only in punctuation or case — `Johar |` / `Johar ||`, `society cluster` / `Society Cluster` — and both halves normalise to one string, so a name-keyed map kept one twin and filed the other's orders at it (production orders 1472 and 2519). The name is a fallback for a branch nobody has pinned yet, and it never matches a branch pinned to a different id; that case is refused as `BRANCH_NOT_FOUND` with a pointer at `sync:ke`. An order already filed at the wrong twin is moved by `npm run repair:ke-order-branches` (dry-run, digest-gated, rollback-able), which also recomputes the branch/month budget rows it touches — the backfill cannot, because a month whose only order left produces no consumption row.
  - **An order whose tax split does not reproduce its own total is rejected, not fatal** (`TAX_SPLIT_MISMATCH`). Legacy is inconsistent about VAT: most orders price inclusive of it, a few add it on top (order 50 is one line at 355 against a GrandTotal of 418.90). Importing one of those under the inclusive model would understate the money, so it is refused — per order, so one bad row cannot block the rest of the history.
- **Consumption is one number with two sources, and they have to agree** (`plans/OF-BUDGET-ledger-orders-parity.md`). What a branch has consumed is `spent + held` — fulfilled spend **plus the hold behind pending and approved orders** — and it is answered either from the `budgets` ledger's running totals or by re-aggregating `orders` for a window. `GET /api/v1/analytics/budgets/summary` picks between them on `useOrderScopedSpending` (`preset !== "all"` plus any date/month/year filter), because the ledger has no grain finer than a month and a part-month selection needs the orders; `loadBranchBudgets` in `lib/server/executive-analytics-queries.ts` reads the orders for the same reason. The two only agree while three rules are stated once, so they are: **(1)** the status buckets and the refund netting `max(0, total − refund)` live in `lib/budget-consumption.ts` (derived from `getOrderStatusesForFilter`, so a new fulfilment status reaches the money with the rest of the app) and in its SQL counterpart `lib/server/budget-consumption-sql.ts` — no reader may restate either inline; **(2)** an order's period is the **UTC** `YYYY-MM` of `created_at`, named by `budgetPeriodOf` and by nothing else. That is the row the creation hold, the fulfilment move and the rejection release all target, so the orders aggregation says `AT TIME ZONE 'UTC'` explicitly rather than inheriting the Postgres session's zone. It is deliberately **not** the Asia/Karachi month `buildAppMonthPeriods` uses — that one selects *which* periods a report covers, this one names *one* row; **(3)** a refund is withdrawn from **the order's own period**, never from today's, and the same-month refund window is judged with `isSameBudgetPeriod` rather than local `Date.getMonth()`. `lib/server/budget-consumption-contract.test.ts` is the control and lists every reader and every period writer — a new one goes on it or it is silently free to drift; `tests/integration/budget-ledger-orders-parity.test.ts` carries the hand-worked oracle and the cross-tenant cases. The branch set this route reports on is fenced in `loadActiveBudgetBranches`: a `branchIds` query parameter is intersected with the caller's organization, and `SINGLE_BRANCH_BUDGET_ROLES` read their own branch whatever the query string names. **K-Electric is the one tenant whose ledger is keyed on the Karachi month instead** — allocations from legacy's own tenure and spend from `backfill-ke-budget-spend.ts`, reconciled to the rupee against legacy's remaining figure — so its ledger and its order-derived figures name different months for an order raised 19:00–23:59:59 UTC on the last day of a UTC month. That gap predates this rule and is **deliberately not repaired**: legacy is the customer's own Karachi-based system and re-bucketing would break the reconciliation. `npm run audit:ke-budget-periods` measures it read-only; there is no `--commit`.
- **One-time add-on budgets carry a validity date, and the expiry is materialised onto the row** (`plans/OF-BUDGET-addon-validity.md`). A branch's money budget is one pool — `remaining = allocated + credited − spent − held` — and `budgets.amount_credited_cents` is read directly by the order hold, group orders, analytics, exports and the KE scripts, so an expired add-on is never subtracted at read time; it is withdrawn from the column. Every add-on that credits money (`PUT /api/v1/budgets`, `type: "addon"`, amount > 0) must carry `validUntil` (`YYYY-MM-DD`, resolved to 23:59:59 Asia/Karachi, today or later) and **is filed on the row for the month that date is in**, which must be one `addonPeriodsOpenAt` allows: the engine's **UTC** period or the administrator's Karachi month — the same month except 00:00–05:00 Karachi on the 1st, when a new-month date opens next month's row at the baseline rather than being refused. When that instant passes, `settleDueAddonsOnBudget` (`lib/server/budget-addon-expiry.ts`) withdraws `min(addonAmount, remaining)` — the **ceiling model**: base is spent first, spent and held are never touched, the check constraint always holds — records it on the `budget_addons` row (`expired_at`, `forfeited_cents`) and in `audit_logs` (`EXPIRE_BUDGET_ADDON`). The arithmetic is pure in `lib/budget-addon-expiry.ts`. **Every path that takes a hold settles under its own `FOR UPDATE` first** (orders POST, orders PATCH, group order creation); budget reads and writes settle too, and `POST /api/v1/budgets/cron/expire-addons` sweeps the rest behind `CRON_SECRET`. `lib/server/budget-addon-expiry.test.ts` pins that list — a new spending path goes on it. A row with `valid_until IS NULL` predates validity and is never settled. Refund credits land in the same column and are treated as non-expiring ceiling. A branch id on the budgets GET query string is fenced to the caller's tenant **before** `loadSingleBranchBudget`, because that load opens a period row when one is missing (`queriedBranchAccessError`, sharing `tenantFenceError` with the PUT).
- **A month's budget row opens lazily, at the branch baseline** (`plans/OF-BUDGET-open-current-month-on-budget-list.md`). No schedule writes it: the first order pre-flight, shop budget read, allocation, or Budgets list load of the month inserts it at `branches.baseline_budget_cents` — never at last month's allocation, so a figure written only into a month row (as the KE imports did) does not roll over. The Budgets list (`loadAggregatedMoneyBudgets`) opens the engine's **UTC** month for the branches it lists, through `openCurrentBudgetPeriodRows` (`lib/server/budget-period-opening.ts`): active branches of budget-enabled tenants inside the caller's fence, positive baseline only, insert-only (`ON CONFLICT DO NOTHING`), never a past month and never the Karachi month while it is ahead of the engine.
- **No order is fulfilled before it is delivered, whoever asks.** Every path to `FULFILLED` — the Super Admin `POST /api/v1/orders/[id]/fulfill`, a token hand-off from any of the five roles that may send one, a delivery that settles a waiting hand-off, and the 48-hour auto-fulfil sweep — requires `fulfillment_status = 'DELIVERED'` first. `fulfillApprovedOrder` (`lib/server/order-fulfillment.ts`) enforces it unconditionally in its single-winner claim (an undelivered order is `"conflict"`), and the fulfil route refuses earlier with 409 via `isOrderDelivered` (`lib/fulfillment-status.ts`). Delivery is recorded only through `POST /api/v1/orders/[id]/fulfillment-status`; fulfilment never records it, and never overwrites `delivered_at`. A token handed over before delivery is remembered and settles the order when the delivery is recorded. Do not reintroduce a mode that fulfils and delivers in one step.
- **Group orders belong to the branch, not just to the requester**: a Group Order Portal submission is recorded as one ordinary `orders` row per branch, carrying a nullable `groupOrderId` back-reference. Every branch-scoped and organization-scoped read therefore already returns them — `BRANCH_ADMIN` and `HEAD_OFFICE` see and decide them with no special case, and **no query may ever add a `groupOrderId IS NULL` filter**. `ORDER_PORTAL` is the one role narrowed by creator, and it is narrowed to *own orders **or** group orders for its branch* (`lib/group-order-visibility.ts`), because a group order spends that branch's budget. Reports that attribute orders to a user must filter creators through `ORDER_CREATOR_ROLES`, never `roles.name = 'ORDER_PORTAL'` alone, or the group requester's orders vanish from the branch's own figures.
- **The branch owns its orders — writes follow branch assignment, not authorship** (`lib/order-write-access.ts`). Either requester role may **edit** a pending order or **request a refund** on any order at a branch it is assigned to, whoever raised it: `ORDER_PORTAL` for its own branch (group orders included), `GROUP_ORDER_PORTAL` across its resolved assignment set (orders raised by branch staff included). The branch set is resolved server-side — `scope.branchId` for the single-branch role, `resolveScopedBranchIds()` for the group role — and **an empty set denies everything rather than widening to the tenant**. This reversed an earlier creator-equality rule, which was proving branch membership and personal accountability at once; only the first survives. The second moved to the trail: every cross-actor write records `onBehalfOfUserId` in its audit row and notifies the raiser through `notifyRaiserOfOrderWrite`, on the same transaction, so a rolled-back edit never announces itself. Deciding an order did **not** widen — approve, reject, fulfil and payment-status still refuse `GROUP_ORDER_PORTAL` — and neither did the invoice, which stays with the raiser. See `plans/OF-GROUP-branch-owns-order-writes.md`. **The fulfilment token hand-off is open to all five operational roles** (`HEAD_OFFICE`, `GROUP_USER`, `BRANCH_ADMIN`, `GROUP_ORDER_PORTAL`, `ORDER_PORTAL`) on any approved order already inside their read scope, regardless of who raised or approved it or the tenant's configured approver role. `canViewFulfillmentToken` (`lib/fulfillment-token-access.ts`) is now a role-and-status rule only; the scope is the caller's job — every surface that releases a token must first fence the order to the actor's tenant/branch/assignments, and `send-token-email` additionally holds `ORDER_PORTAL` to `canOrderPortalReadOrder` (own orders or group orders for its branch), so a guessed id cannot release a colleague's token.
- **Budget-burn watchlist ("Users to review")**: `GET /api/v1/analytics/executive/budget-burn` draws every requester's consumption in each of the `BUDGET_BURN_PATTERN_MONTHS` (3) Karachi calendar months ending with the selected one, and highlights the newest where it is at least `momSpikePct` (15%) above the one before it, from a previous month of at least `momMinBaselineCents` (₨5,000) (`plans/OF-BUDGET-BURN-three-month-pattern-mom-flag.md`, narrowing `plans/OF-BUDGET-BURN-watchlist.md`). **The percentage is a ratio of the last two cells on the row and of nothing else**, so a reader can check it without leaving the row; `monthWindows` carries the buckets as `pattern[]`, oldest first, the last being the selected month itself. It is presentation only — nothing is approved, blocked or charged from a highlight. Every rule is pure in `lib/budget-burn-risk.ts` (`monthOverMonth` is the single highlight rule, shared with the item panel) and every threshold is an exported constant the UI prints. Six rules are load-bearing: **(1)** it is narrower than the Center — `BUDGET_BURN_ROLES` is `SUPER_ADMIN` and `HEAD_OFFICE`, checked *after* `resolveExecutiveScope`, and `GROUP_USER` is refused although the Center admits it; **(2)** *every* creator's orders count toward the branch denominator but only `ORDER_CREATOR_ROLES` are listed, keyed on `orders.branch_id` (the budget spent), never `users.branch_id`; **(3)** the listed set is the **union across every pattern month** (`unionCreators`), because a requester who consumed last month and nothing this month is the shape the panel exists to show — while Share, Orders, the late window and the branch denominators stay on the selected month alone (`summarizeCreators(currentRows, …)`); **(4)** each month cell is Consumed (Spend + Pending, pending broken out on the cell) and drills into **that month** with `statuses=consumed` (`DRILLDOWN_STATUS_SETS` in `lib/executive-analytics.ts`, `CONSUMED_ELIGIBLE_FILTER` in `lib/metric-utils.ts`). Product Performance Amount uses that same allowlisted status set for compare, matrix, options, and drill-down; its Quantity view and the other executive charts keep the `revenue` default; **(5)** the item-wise panel reads the **same buckets in the same order** and highlights by the same rule, so its column totals equal the cells above it — reading any other window would let it contradict, silently, the figure clicked to open it; **(6)** a highlight is never carried by colour alone — every highlighted cell also carries `HIGHLIGHT_MARKER` and an accessible label naming both months, both amounts and the threshold. The multi-signal `score`/`reasons` behind the retired shortlist are still computed and still returned (`scoreFlaggedCount`), but nothing on the panel reads them; delete them deliberately or not at all. The aggregate borrows `orderConditions` for its fence, stays at order grain, and issues one bounded read per pattern month; `lib/server/budget-burn-queries.test.ts` pins that, and `tests/integration/budget-burn-api.test.ts` carries the hand-worked oracle.
- **Ordering stops at two unpaid invoices, per branch, when the organization opts in** (`plans/OF-PAYMENT-CONTROL-unpaid-invoice-ordering-block.md`). Super Admin sets `organizations.block_ordering_on_unpaid_invoices` in Create/Edit Company (default off; audited as `UPDATE_UNPAID_INVOICE_ORDERING_BLOCK`). With it on, `lib/server/overdue-payment-source.ts` — the payment-control seam, which answered "not configured" before — counts the branch's orders that are `FULFILLED` + `DELIVERED` + invoiced + `UNPAID` (`isUnpaidInvoiceOrder` in `lib/unpaid-invoice-block.ts`): exactly the orders the Super Admin Paid/Unpaid control can act on, so every block can be cleared by paying. At `PAYMENT_CONTROL_POLICY.overdueBlockThreshold` (2) the existing gate refuses the order in both creation paths — 409 `PAYMENT_CONTROL_BLOCKED` single-branch, a per-branch `failed` result with `code` and `unpaidInvoiceCount` in a group submission — and the shop and group storefront turn that into the "please pay your dues" popup. The shop's pre-check (`lib/ordering-block-check.ts`) is presentation only and fails open; the gate is the control. A Head Office exception still lets a blocked branch order. The seam returns no amounts, because the status route is readable where prices are hidden. **K-Electric's imported orders default to `UNPAID`**: do not switch this on for a tenant whose payment status is not maintained, or every branch with two delivered orders stops ordering at once.
- **Ordering also stops at two delivered-but-unacknowledged orders, per branch, when the organization opts in** (`plans/OF-ORDERS-unacknowledged-delivery-ordering-block.md`). A separate toggle, `organizations.block_ordering_on_unacknowledged_deliveries` (Super Admin only, default off, audited as `UPDATE_UNACKNOWLEDGED_DELIVERY_ORDERING_BLOCK`), and a separate gate, `assertBranchDeliveriesAcknowledged` in `lib/server/unacknowledged-delivery-block.ts`, called in both creation paths **right after** the payment-control gate and before any lock or write — so with both on, the unpaid-invoice refusal wins. An unacknowledged delivery is `status = 'APPROVED'` and `fulfillment_status = 'DELIVERED'`, counted with the dashboard's own `viewerStatusBucketCondition("DELIVERED_UNACKNOWLEDGED")`, so the popup's number and the dashboard's "Delivered/Unacknowledged" figure cannot disagree; every order at the branch counts, whoever raised it, group orders included. Threshold `UNACKNOWLEDGED_DELIVERY_BLOCK_THRESHOLD` (2). Refusal: 409 `UNACKNOWLEDGED_DELIVERIES_BLOCKED` single-branch, a tagged per-branch `failed` result (`unacknowledgedDeliveryCount`) in a group submission. There is **no Head Office exception**: the branch clears it itself by handing the fulfilment token over (which settles a delivered order to `FULFILLED`), and the 48-hour auto-fulfil sweep clears it too. Only new orders are gated, never an edit. The shop pre-check is `GET /api/v1/orders/delivery-acknowledgement`, fenced exactly like `GET /api/v1/payment-control`, returning a count and threshold only — never order references, because an Order Portal user may not see every order at their branch. **K-Electric carries a large delivered-unacknowledged backlog**: clear it before switching this on there.
- **Budget allocation is a per-organization switch, and an order's budget treatment is fixed when it is created** (`plans/OF-BUDGET-organization-budget-toggle.md`). Super Admin sets `organizations.budgets_enabled` in Create/Edit Company (audited as `UPDATE_ORGANIZATION_BUDGETS_ENABLED`). **The column defaults to `true`** so existing tenants, fixtures and scripts that insert an organization directly keep their budgets; **the product default is off** — `organizationCreateSchema` defaults the field to `false` and the form starts unticked. With it off, neither creation path reads, opens, checks or holds a budget (money or quantity), quantity mode never narrows a catalogue, budget reads answer `budgetsEnabled: false` **without writing a period row**, and budget writes are 409 `BUDGETS_DISABLED`. Each order records the setting it was created under in `orders.budget_tracked` (read under `FOR SHARE` on the organization row by `resolveOrderBudgetTracking`; the PATCH holds `FOR UPDATE`), and **every later ledger move — edit, reject, fulfil, auto-fulfil, both refund paths, admin delete — asks `orderTakesBudget(order)`, never the tenant's current setting**; it throws when the column was not selected rather than guess. That is what stops a switch from making a rejection release another order's hold, or a fulfilment fail on a hold that was never taken. Budget figures come only from budget-enabled tenants (`budgetEnabledBranchSql`) and only from tracked orders (`budgetTrackedOrderSql`); order figures are unaffected. `lib/server/organization-budget-policy-contract.test.ts` lists every ledger mover and budget reader — a new one goes on it; `tests/integration/organization-budget-toggle.test.ts` carries the hand-worked ledger oracle across both switch directions. **Apply the migration before deploying**: the code selects both columns.
- **The activity log has two readers** (`plans/OF-AUDIT-head-office-activity-log.md`, reversing the Head Office refusal in `plans/OF-AUDIT-admin-activity-log.md`). `/activity` and `GET /api/v1/activity-logs`: Super Admin reads every tenant (`SYSTEM_VIEW_AUDIT_LOGS`); Head Office reads **its own organization only** (`ORG_VIEW_AUDIT_LOGS`); every other role is 403. The rule is `lib/activity-log-access.ts` (`resolveActivityLogReach`, `applyActivityReach`), and the organization comes from `getRequestScope()` — the `users` row — never the request; a Head Office account with no organization is refused, not widened. `ActivityFilters.reach` is **required and separate from the `organizationId` filter**, and an organization reach puts `organization_id = $org` into all three branches of the union (`lib/server/activity-log-sql.ts`), so platform rows and other tenants never appear; an `organizationId` naming another tenant is 403. For that reader, anyone outside the tenant — in practice Apricart staff — is **anonymised** by `lib/activity-log-reach.ts`: no id, email, name, IP or user agent, actor-identifying metadata keys withheld, the row labelled "Apricart administrator". To stop search becoming an oracle on hidden people, people are resolved only within the tenant, the trail's own actor-email/actor-id columns are not searched, and an `actorId` outside the tenant reads as empty. `tests/integration/activity-log-api.test.ts` ("Head Office reads its own organization") carries the cross-tenant cases.
- **Head Office asks for new products; Super Admin decides** (`plans/OF-PRODUCT-REQUEST-head-office-new-product-requests.md`). Product Catalog → Product Requests (`/inventory/product-requests`) for both roles. `POST /api/v1/product-requests` is `HEAD_OFFICE` only, every field optional but not all empty, tenant re-read from the user row; `GET` shows Head Office its whole organization's requests and Super Admin every tenant's; `PATCH /api/v1/product-requests/[id]` is `SUPER_ADMIN` only, row-locked, and moves a request along `PRODUCT_REQUEST_TRANSITIONS` (`lib/product-request.ts`): `PENDING → UNDER_REVIEW` (optional, records who and when), and `PENDING | UNDER_REVIEW → APPROVED | REJECTED`; a decision is final (409). **An approval must carry `estimatedAvailableOn`** — the day Head Office is told the product will be in the catalogue, Karachi today to +365 days, checked by `productRequestAvailabilityRefusal` against `now` rather than in the schema; approvals from before the date existed keep null (`plans/OF-PRODUCT-REQUEST-review-stage-and-availability-date.md`). The rule is role allowlists in `lib/product-request-access.ts`, deliberately **not** `Permission` keys — `ROLE_TEMPLATES.SUPER_ADMIN` would hold a "raise" key by construction. A request is information only: approving it creates no product, and `expected_price_cents` is never read by the price ladder. **`POST /api/v1/upload/image` admits Head Office** for the request's picture, because it is the one raster path the production WAF allows; do not narrow it back to Super Admin without giving the request form another upload path (and a WAF rule). The stored image must pass `isStoredImagePath` — `product_requests_image_path_ck` backs that up — and the form refuses a body over 8000 bytes because the WAF blocks bodies over 8 KB.
- **Apricart's Order Desk (`ORDER_DESK`) keys in orders customers send by email or WhatsApp** (`plans/OF-ORDER-DESK-internal-order-entry.md`). A desk user has **no organization**; its reach is the intersection of two Super Admin grants, re-read from the database on every request — `organizations.managed_ordering` (default off, audited `UPDATE_ORGANIZATION_MANAGED_ORDERING`) **and** a row in `order_desk_assignments` (an organization with `branch_id` null = every branch, or one branch; audited `UPDATE_ORDER_DESK_ASSIGNMENTS`). All rules are pure in `lib/order-desk-access.ts` (`resolveDeskReach`); the rows are loaded by `lib/server/order-desk-scope.ts`. The assignments are a table of their own on purpose — never put a desk user in `user_branch_assignments`, which feeds the group roles' reports. **`proxy.ts` refuses a desk token every API call not in `ORDER_DESK_API_RULES`**, because most handlers check roles inline and a null organization can read as "no tenant filter"; a new desk endpoint goes on that list *and* checks `requireApiRole(["ORDER_DESK"])` plus the reach itself (`lib/order-desk-access.test.ts` enforces both). Desk orders go through the shared `POST /api/v1/orders` and are created `APPROVED` whatever the tenant's approval switch (`resolveInitialOrderApproval` gets the creator; `approved_by_user_id` = the desk user), must carry `intake_channel` + `intake_reference` (refused on every other order), queue no notification, and are re-checked under `FOR SHARE` inside the creation transaction. The desk acts **only on orders it entered** (`created_by_role = 'ORDER_DESK'`). **Delivery is not the desk's to record**: Super Admin moves it through the existing progress route, and the desk then fulfils through `POST /api/v1/order-desk/orders/[id]/fulfil` (`fulfillApprovedOrder`, no token) — the Super Admin fulfil/progress routes are untouched. Before delivery the desk may **cancel** (`CANCELLED`, reason required; hold, quantity hold and stock released by the order's own period — `lib/server/order-desk-orders.ts`) or **edit** (`lib/server/order-desk-edit.ts`: re-priced, stock and hold moved by the difference, add-ons settled first, invoice number kept — a separate path because the requester edit is PENDING-only). After fulfilment it may **request** a refund through the shared refund route, PENDING until Super Admin approves. The customer's **screenshot** goes through `POST /api/v1/upload/image` (the WAF-allowed path) but is stored under the private `order-intake/` prefix, never as a `data:` URL, answered with a key not a path, bound to its uploader by the `UPLOAD_ORDER_INTAKE_ATTACHMENT` audit row and to one order by `orders_intake_attachment_key_uq`; it is served only by `GET /api/v1/order-desk/orders/[id]/attachment`, behind the desk's reach. Only Super Admin creates or manages a desk user (`ROLE_LEVEL` puts it above Head Office for that reason alone), and the access route never switches an account into or out of the role. `POST /api/v1/orders` is now role-allowlisted (`lib/order-creation-access.ts`): a `VIEWER` is refused; `EMPLOYEE` is kept.
- **Apricart's management reads delivery performance across every tenant** (`plans/OF-DELIVERY-management-delivery-dashboard.md`). The `APRICART_EXECUTIVE` role is read-only, has **no organization**, is created by Super Admin only (`ROLE_LEVEL` 7, beside `ORDER_DESK`), cannot be switched into or out of, and is confined by `proxy.ts` to `/executive` and `APRICART_EXECUTIVE_API_RULES` (`lib/apricart-executive-access.ts`) — the two `GET /api/v1/delivery-dashboard*` reads plus the password-change endpoints; a new executive endpoint goes on that list *and* checks the role itself (`lib/apricart-executive-access.test.ts` enforces both). Super Admin reads the same dashboard at `/delivery-dashboard`. **Health is computed at read time, never stored**, by `assessDelivery` in `lib/delivery-sla.ts`: 72 calendar hours from `approved_at`, due soon in the last 12, stopped by `delivered_at` (written once by the progress route, never by fulfilment). Open = `APPROVED` and not `DELIVERED`, the Viewer's `UNFULFILLED`. Only orders approved from **2026-09-01 Karachi** count, and **never a `legacy_order_imports` row** — imported timestamps are import times. Destination city is the delivery address's, else the branch's; region is `branches.region` (`NORTH`/`CENTRAL`/`SOUTH`, `branches_region_ck`), which **only Super Admin sets** — both branch write routes refuse it from Head Office. The responses carry no amount and no person; keep it that way, or price visibility starts to apply. `tests/integration/delivery-dashboard-api.test.ts` carries the oracle.
- **No order is marked delivered without its delivery challan** (`plans/OF-DELIVERY-CHALLAN-proof-of-delivery.md`). Super Admin uploads the challan through `POST /api/v1/upload/image` with `purpose=delivery-challan` and `orderId` (the one upload path the production WAF allows; every other role is 403 for that purpose), and `POST /api/v1/orders/[id]/fulfillment-status` refuses `DELIVERED` without a `deliveryChallanId` — and refuses one at any other stage. The upload stores an **unattached** `order_delivery_challans` row bound to that order and that uploader; the delivery attaches it in the **same transaction** as the status change (`attachDeliveryChallan`), matching only this order, this Super Admin, never attached — otherwise the whole transition rolls back. Images are re-encoded through `sharp`; a PDF is not re-encoded but inspected by `inspectPdfUpload` (`lib/server/pdf-upload-security.ts`) and refused if it carries script, actions, embedded files, XFA or encryption, including inside compressed object streams. Files live under the private `delivery-challan/` S3 prefix, which `isValidImageKey` never accepts, so the public image route cannot serve one. **Reading follows the order exactly**: `GET /api/v1/orders/[id]/delivery-challan` and `.../[challanId]/file` use `canReadOrderDetail` (`lib/server/order-read-access.ts`), the same rule as `GET /api/v1/orders/[id]` — out of scope is 404, `VIEWER` and the desk/executive roles are 403. The file is served `private, no-store`, `nosniff`, sandboxed, a PDF always as an attachment. Super Admin may **replace** a delivered order's challan (`POST /api/v1/orders/[id]/delivery-challan`); the old one is kept, marked replaced, visible to Super Admin only. One current challan per order is enforced by `order_delivery_challans_current_uq`. `tests/integration/delivery-challan-api.test.ts` carries the role matrix; suites that only need to record a delivery use `stageDeliveryChallan` from `tests/integration/helpers/delivery-challan-fixtures.ts`. **Apply the migration before deploying, and confirm on staging that the WAF lets a PDF through the upload path.**
- **Table column sorting** (`plans/OF-TABLE-column-sorting.md`): every header in the Orders table and every Reports table sorts, through `SortableHeader` / `useTableSort` (`components/reports/sortable-header.tsx`) and the pure rules in `lib/table-sort.ts`. A table that holds the whole filtered set sorts on the client with `sortRows`; a **paginated** one (Orders, Order Report, Refund Report) must sort on the server, or it would reorder one page and present it as the whole list — it sends `sort=&dir=`, and the route admits only keys from its allowlist in `lib/list-sort-keys.ts` (anything else is 400), maps them through a `Record<Key, SQL>` and `orderBySortSql`, and drops price keys via `sortKeysForCaller` when prices are hidden, because ordering by a redacted figure still discloses its ranking. `lib/server/table-sort-contract.test.ts` lists every sortable table and every server-sorted route; a new header cell or report table goes on it.
- **Permissions**: Check `lib/permissions.ts` before adding any new admin-only feature — never inline permission logic in components.
