# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**OneFlowe** is a multi-tenant retail operations platform for Apricart. It has three distinct portals:
- **Super Admin portal** — global inventory, organizations, branches, and platform-level configuration
- **Organization/Branch portal** — day-to-day operations, budgets, orders, and inventory per org/branch
- **Order Portal** — employee-facing e-commerce interface for placing internal orders (`/shop`)

## Commands

```bash
# Development
npm run dev           # Start dev server with Turbopack (preferred)
npm run dev:legacy    # Start dev server with webpack (fallback if Turbopack issues)

npm run lint

npm run db:migrate:dev   # Migrate the local database (localhost only; .env.development.local, then .env.local)

npm run db:bootstrap-admin -- --confirm=CREATE_SUPER_ADMIN  # One-time admin bootstrap
npm run db:studio     # Open Drizzle Studio UI for inspection

# Data import

```

### Testing

```bash
npm run test:watch     # same, in watch mode
npm run test:integration  # needs a disposable Postgres; skips itself without one
npm run test:all       # both projects
npm run typecheck
```

Two Vitest projects: `vitest.config.ts` (jsdom, tests beside the code) and
`vitest.integration.config.ts` (node, `tests/integration/**`, one file at a

database whose name contains `test`; without it they skip and the command still

## Architecture

### Tech Stack
- **Framework**: Next.js 15 App Router (TypeScript)
- **UI**: shadcn/ui (New York style) + Radix UI + Tailwind CSS 4
- **Database**: PostgreSQL via Drizzle ORM (schema at `db/schema.ts`, migrations in `drizzle/`)
- **Auth**: NextAuth.js credentials provider — encrypted JWT cookies backed by a per-browser revocation registry, with a 1-15-minute tenant idle timeout and fixed 8-hour absolute lifetime
- **Cache/MFA**: Redis via Upstash
- **Storage**: AWS S3
- **Email**: Nodemailer (SMTP)
- **Charts**: Recharts
- **PDF/Export**: jsPDF + xlsx

### Role-Based Routing

The request proxy (`proxy.ts`) enforces routing by role:
- `ORDER_PORTAL` users → only `/shop/*`
- All other roles → `/dashboard` and portal pages; redirected away from `/shop`
- Four roles: `SUPER_ADMIN`, `HEAD_OFFICE`, `BRANCH_ADMIN`, `ORDER_PORTAL`
- Granular permissions live in `rolePermissions` table, evaluated via `lib/permissions.ts`

## Important Patterns

- **API routes** follow the pattern `app/api/v1/<resource>/route.ts` and use `lib/error-handler.ts` for consistent error responses.
- **Server components vs client components**: API data fetching happens in client components via `lib/hooks/` and `lib/api.ts`; use `"use client"` at the top of interactive components.
- **Inventory cascade**: When inventory changes at the global level, `lib/inventory-cascade.ts` propagates changes down to org and branch levels. Always go through this utility rather than writing directly.
- **Pricing — resolving**: A product's price is layered — group override, then organization override, then global base price. Always resolve it through `lib/server/effective-price.ts` (`resolveEffectivePriceCents`, `effectivePriceCentsSql`, `scopedOverrideCentsSql`); never write a `customPrice ?? basePrice` expression by hand, or the price charged and the price displayed will drift. The group tier applies only where exactly one group is in scope (a branch, or an authorized group-portal submission).
- **Pricing — the downward rule**: A price change never reaches past a tier that has set its own price. Changing the global base price does **not** touch any organization or group price, whatever their values happen to be; changing an organization price does not touch the global one, and reaches groups only as the administrator chose; changing a group price touches nothing above it. `cascadeGlobalProductFieldUpdate` cascades descriptive fields only (`CASCADABLE_GLOBAL_FIELDS`) — never `basePrice`.
- **Pricing — propagating**: Changing an organization price moves every group that has no override of its own, because those groups inherit it. `lib/group-price-propagation.ts` turns an administrator's choice into a plan: `all` (clear group overrides so everyone follows), `selected` (the chosen groups follow; every other unpriced group is *pinned* at its current price so it does not drift), or `none` (the default and the pre-existing behaviour). The planner is pure and shared — the confirmation dialog previews with it and the server rebuilds the plan with it from rows read **before** the price update, inside the same transaction. Clients send a mode, never a plan.
- **Pricing — changing**: **Only `SUPER_ADMIN` may write a price, at any tier.** The rule lives in `lib/pricing-access.ts` (`canMutatePrices`, `priceMutationFailure`, `rejectPriceFieldsForRole`) and is carried in RBAC as `Permission.PRICING_MANAGE`, granted to Super Admin alone. Administering a catalogue, tenant, or group does not carry the right to change what anyone is charged — Head Office may read prices but never set them. Any new endpoint that writes a price column must go through that module and be added to the route list in `lib/pricing-access.test.ts`. Reading a price is a separate concern, governed by `lib/price-visibility.ts`.
- **Image storage**: Uploaded images live in S3, never in the database. `POST /api/v1/upload/image` sanitises through `sharp`, writes the object, and returns an application path (`/api/v1/images/products/<uuid>.<ext>`) which is what gets stored in `imageUrl`/`customImageUrl`. `GET /api/v1/images/*` streams it back to signed-in users; the bucket itself is private. Rows written before this change still hold `data:` URLs and still render — use `isDataUrl`/`isStoredImagePath` from `lib/server/image-storage.ts` to tell the two apart, and `npm run migrate:images-to-s3` to move the remainder. Never write a `data:` URL to a column.
- **Mirrored accounts and email login**: A user row with `external_source` set was mirrored from another system and **cannot sign in with an email address** — only with its username (`lib/auth-options.ts`, `loadStaffLoginRecord`). Such a person holds one account per role behind a single shared email (`<employee code>-ba` to approve, `-op` to order), so an email alone cannot say which portal they meant. Accounts created in the portal leave `external_source` null and keep email-or-username login. Never relax that guard to "fix" a login complaint from a K-Electric user; point them at their username.
- **Forced password change and the emailed proof**: every K-Electric account was flagged `must_change_password` on 2026-09-17; the flagged session is sent to `/change-password` and refused on every other `/api/v1/*` path (`lib/password-change-pending.ts`). The change itself (`lib/server/password-change.ts`) was gated on a `VERIFY_EMAIL` code entered on the same session. **That proof is switched off for now** by `PASSWORD_CHANGE_EMAIL_VERIFICATION` in `lib/password-change-policy.ts` — a constant in code, deliberately not an environment variable, read by the server module and the page alike (`plans/OF-KE-password-change-without-email-verification.md`). With it off, the change still requires the current password, the policy, new ≠ old, still clears the flag, bumps `session_version` and drops every session, and still has to find the token's own live `auth_sessions` row (only the freshness term goes); the audit row says `emailVerified: false`. To re-enable, set the constant back to `"required"` and update `lib/password-change-policy.test.ts`. The required path keeps running in `tests/integration/password-rotation.test.ts` (policy mocked on); the shipped path in `tests/integration/password-change-direct.test.ts`.
- **Self-service password reset** (`plans/OF-AUTH-self-service-password-reset.md`): `/forgot-password` → `POST /api/v1/auth/password-reset/{request,verify,complete}`, all public, logic in `lib/server/password-reset.ts`, state in `password_reset_challenges` (HMAC digests only, never the code or token; one live challenge per account by partial unique index). It follows login's identifier rules — a mirrored account resets by username, never by email, and an email naming more than one account resets nothing. **The request step must not reveal whether an account exists, by body or by timing**: every input gets a 202 and a challenge id (a random decoy for non-accounts), the email is sent via `after()` rather than before the response, and the response is held to `PASSWORD_RESET_REQUEST_MIN_RESPONSE_MS`. For the same reason the verify step never reports remaining attempts. Completion bumps `session_version`, revokes every `auth_sessions` row and clears `must_change_password` and the lockout. Both the Order Portal profile menu (`components/auth/order-portal-profile-menu.tsx`, used by `/shop` and the group storefront) and the admin topbar link to it. `tests/integration/password-reset.test.ts` carries the database behaviour.
- **Self-service joining is locked to the organization's email domain** (`plans/OF-JOIN-email-domain-lock.md`, building on `plans/OF-JOIN-organization-self-service-join.md`). Super Admin sets `organizations.email_domain` in Create/Edit Company; the join form fixes it as the address suffix, and `POST /api/v1/join/requests` refuses — before hashing or storing anything — an organization with no domain (409) or an address not at exactly that domain (400, no subdomains), judged against the domain re-read with the code on that request (`joinEmailDomainRefusal`), never one the page sends back. The lookup answers a domainless organization with `emailDomain: null` and no branches or groups, and the page shows a "contact your organization" prompt instead of the form. Every rule is in `lib/organization-email-domain.ts` and pinned by `organizations_email_domain_shape_ck`. **The column is deliberately not unique**: K-Electric and K-E-Demo share addresses and so share a domain — the join code selects the tenant, the domain only restricts what an applicant may type.
- **K-Electric legacy sync**: Reference data comes from the legacy platform via `npm run sync:ke` (organization, branches, groups, catalogue, users), and orders via `npm run import:ke-orders` — in that order, because an order cannot be written until its branch, ordering user **and products** exist. Both are dry-run by default and require the plan digest they print in order to commit. Planning logic is pure and lives in `lib/legacy-import/ke-sync.ts` and `lib/legacy-import/ke-products.ts`; branches are matched by `external_id`, never by name once pinned. Organization 2 (`K-E-Demo`) shares many of the same emails and must never be touched.
  - **The target organization is resolved by `--organization-code`, not compiled in** (default `0001`). Both scripts refuse if that code belongs to a differently-named tenant, and `sync-ke.ts` creates the organization only with `--create-organization`. This is what lets the whole sync be rehearsed on a test database, where `0001` is taken by another tenant. The two scripts must always be pointed at the same code or the orders land in a tenant the sync never populated.
  - **The sync creates catalogue entries and groups, and writes `base_price`.** It previously refused both because pricing is `SUPER_ADMIN`-only; the refusal was reversed because the order import rejects every line as `PRODUCT_NOT_FOUND` without them. It still never changes the price of a product that already exists — legacy prices per branch, OneFlowe has no per-branch tier, so a new product takes the price most of its branches agree on and every disagreement is reported, not applied. Groups are created with no price of their own.
  - **`normalizeProductName` in `lib/legacy-import/ke-electric.ts` is the single join key** between a legacy order line and the catalogue. `ke-products.ts` re-exports it rather than reimplementing it: a normaliser that merely looks equivalent splits one product into two, and the order line then matches both and is refused as `PRODUCT_AMBIGUOUS`.
  - **A first run against an empty database needs two passes.** People at a branch created in the same run are skipped as `BRANCH_NOT_PINNED`, because the branch did not exist when the plan was built. Re-run and they are picked up; a third run reports nothing to do. Branch budgets follow the same rule, for the same reason.
  - **Branch budgets come from the location rows, not a separate endpoint** (`lib/legacy-import/ke-budgets.ts`). `MonthlyBudget` is the allocation; `TotalBudget` is what is **left**, not what was granted — KE HOUSE carries MonthlyBudget 900,000 against TotalBudget 6. It is never written as an allocation, but it is exactly OneFlowe's `allocated + credited − spent − held` (verified to the rupee across every funded branch), so for a location whose `MonthlyBudget` is 0 yet still has money left (HSEQ: 0 / 5) the allocation is `TotalBudget + our used`. **Legacy is authoritative for the current month's allocation**: a missing row is created, a lower one is raised (always safe under `budgets_values_valid_ck`), a higher one is lowered only with `--lower-budgets` and only if the invariant still holds — otherwise it is reported as drift. A location legacy leaves at 0/0 gets no row of its own (the shop creates one at zero on demand) but a row we already hold for it is compared like any other. The API exposes only the current tenure; historical months still come from the report file via `scripts/import-ke-branch-budgets.ts`. Spend stays the job of `backfill-ke-budget-spend.ts` — and a branch showing exactly 0 remaining is usually a row that backfill created at `allocated = spent + held` before the sync could set the real figure. That is the default mode, `--budgets=legacy`. **`--budgets=zero` is the other one** (`planZeroBudgets`): every active branch's allocation for the month goes to the floor `budgets_values_valid_ck` allows (`spent + held − credited`, so nothing remains to order against), a missing row is created at 0, and **`branches.baseline_budget_cents` is cleared** — two paths in `app/api/v1/budgets/route.ts` re-fund from it (a missing month row is created at the baseline; a zero row with no spend is treated as stale and reset to it), so a zero that keeps the baseline is undone by the next page load. Legacy figures are ignored for that run. `--budgets=skip` leaves budgets alone. Choose the mode deliberately on every run: the default would raise a zeroed month straight back to the legacy figure. **A committed zero run is reversed by `npm run restore:ke-zeroed-budgets`** (`lib/legacy-import/ke-budget-restore.ts`), from the before-values in that run's own commit report — not from legacy, whose figures differ from OneFlowe's on a few locations. It raises each lowered allocation back only if the row still holds what the zero run wrote, puts each cleared baseline back only if it is still 0 (that is what switches the monthly re-allocation on again — no code condition was ever changed), leaves the rows the zero run created at 0 alone, and reports anything that moved since rather than overwriting it. Dry-run and digest-gated like the sync.
  - **Which branch sees which product is the legacy per-location item list, and the sync mirrors it** (`lib/legacy-import/ke-branch-catalogue.ts`). Legacy keeps one item row per product per location (`Item.CategoryID -> Category.LocationID`); a Distribution-group location carries ~63 items, an Enabling-group one ~120. The shop lists a product only when its `branch_inventory` row is visible **and** active, its `organization_inventory` row is active, its `global_products` row is active, and `stock_quantity` covers the order — so the sync does all four: it wakes a global product the KE import parked `inactive` (only one it created — `metadata.legacySource = KE_LOGISTICS` or a `KE-` code; anything another hand retired stays retired), activates the organization entry, gives every product legacy sells `--stock` units (default 500; legacy tracks no stock, OneFlowe decrements it on every order) — a zero-stock product on every run, and every product only with `--reset-stock`, so a figure an administrator typed or orders wore down is not clobbered by a routine sync — and upserts the branch row. It never hides: a product visible at a branch that legacy does not list there is reported as an extra. The Head Office "assign" endpoint skips any existing non-deleted row, visible or not, which is why a dormant row from the legacy order import cannot be surfaced through the UI. Products created in the same run are assigned on the next — the same two-pass rule as branches and people.
  - **`import:ke-orders` defaults to the whole history** and fetches the order list **one calendar month at a time** (`monthWindows`). A single request for twenty months returns ~1MB and the legacy platform answers by throttling or dropping the connection. Detail fetches run at concurrency 3, and 403/429/503 back off exponentially in seconds — sub-second retries just burn the attempt budget and kill the run.
  - **A person's branch comes from `SubuserLocations`, never from `LocationID`** (`legacyLocationOf` in `ke-sync.ts`). `LocationID` looks authoritative and is not — legacy populates it for everyone, overwhelmingly with 2 (KE HOUSE). For 13 of the 148 people the two disagree, and trusting `LocationID` parked all 13 at KE HOUSE, left branches such as GSMP-KKI with no staff at all, and made their orders unattributable. `LocationID` is honoured only when `SubuserLocations` agrees the person is there. The sync also *moves* an existing account that is on the wrong branch (`branchMoves`), because the assignment is legacy's to state, not ours.
  - **An imported order's branch comes from the legacy `LocationID`, never from the location name** (`lib/legacy-import/ke-order-branches.ts`, used by `import-ke-orders.ts`). Legacy has twins whose names differ only in punctuation or case — `Johar |` / `Johar ||`, `society cluster` / `Society Cluster` — and both halves normalise to one string, so a name-keyed map kept one twin and filed the other's orders at it (production orders 1472 and 2519). The name is a fallback for a branch nobody has pinned yet, and it never matches a branch pinned to a different id; that case is refused as `BRANCH_NOT_FOUND` with a pointer at `sync:ke`. An order already filed at the wrong twin is moved by `npm run repair:ke-order-branches` (dry-run, digest-gated, rollback-able), which also recomputes the branch/month budget rows it touches — the backfill cannot, because a month whose only order left produces no consumption row.
  - **An imported order parked on a placeholder creator is given to its person only when the data proves it** (`npm run repair:ke-order-creators`, `lib/legacy-import/ke-order-creators.ts`, `plans/OF-KE-reattribute-placeholder-orders.md`). The importers attributed unmatched takers to inactive `legacy_ke_*@historical.invalid` accounts, and the Order Portal shows a user only orders they created at their own branch, so those people could not see their own history ("the order is not in OneFlowe"). An order moves only from a placeholder, at the branch pinned to its legacy `LocationID`, when that legacy login carries one name throughout and exactly one active `ORDER_PORTAL` `KE_LOGISTICS` account of that name is at the order's branch. **Orders on the retired `checking-<code>-*` accounts are never moved**: the recorded taker name follows the import batch, not the order date, so it cannot say which holder of a reissued code placed an order. Dry-run, digest-gated, rollback-able.
  - **An order whose tax split does not reproduce its own total is rejected, not fatal** (`TAX_SPLIT_MISMATCH`). Legacy is inconsistent about VAT: most orders price inclusive of it, a few add it on top (order 50 is one line at 355 against a GrandTotal of 418.90). Importing one of those under the inclusive model would understate the money, so it is refused — per order, so one bad row cannot block the rest of the history.
- **Consumption is one number with two sources, and they have to agree** (`plans/OF-BUDGET-ledger-orders-parity.md`). What a branch has consumed is `spent + held` — fulfilled spend **plus the hold behind pending and approved orders** — and it is answered either from the `budgets` ledger's running totals or by re-aggregating `orders` for a window. `GET /api/v1/analytics/budgets/summary` picks between them on `useOrderScopedSpending` (`preset !== "all"` plus any date/month/year filter), because the ledger has no grain finer than a month and a part-month selection needs the orders; `loadBranchBudgets` in `lib/server/executive-analytics-queries.ts` reads the orders for the same reason. The two only agree while three rules are stated once, so they are: **(1)** the status buckets and the refund netting `max(0, total − refund)` live in `lib/budget-consumption.ts` (derived from `getOrderStatusesForFilter`, so a new fulfilment status reaches the money with the rest of the app) and in its SQL counterpart `lib/server/budget-consumption-sql.ts` — no reader may restate either inline; **(2)** an order's period is the **UTC** `YYYY-MM` of `created_at`, named by `budgetPeriodOf` and by nothing else. That is the row the creation hold, the fulfilment move and the rejection release all target, so the orders aggregation says `AT TIME ZONE 'UTC'` explicitly rather than inheriting the Postgres session's zone. It is deliberately **not** the Asia/Karachi month `buildAppMonthPeriods` uses — that one selects *which* periods a report covers, this one names *one* row; **(3)** a refund is given back on **the order's own period**, never today's — both refund routes select the row by `budgetPeriodOf(order.createdAt)`, which matters now that a Super Admin may approve a refund months later — and both move it by one rule, `planRefundLedgerMove` (`plans/OF-BUDGET-refund-ledger-debit.md`): a spent order's refund is **withdrawn from `spent`** (at most what the row has spent, any remainder credited), so the ledger nets it exactly as the orders do; an unfulfilled order's refund is credited and its hold left whole, because fulfil, reject and cancel each move the order's full total. The admin route used to credit every refund, which the date-filtered budget summary then counted twice; rows approved before the change still hold those credits. `lib/server/budget-consumption-contract.test.ts` is the control and lists every reader and every period writer — a new one goes on it or it is silently free to drift; `tests/integration/budget-ledger-orders-parity.test.ts` carries the hand-worked oracle and the cross-tenant cases. The branch set this route reports on is fenced in `loadActiveBudgetBranches`: a `branchIds` query parameter is intersected with the caller's organization, and `SINGLE_BRANCH_BUDGET_ROLES` read their own branch whatever the query string names. **K-Electric is the one tenant whose ledger is keyed on the Karachi month instead** — allocations from legacy's own tenure and spend from `backfill-ke-budget-spend.ts`, reconciled to the rupee against legacy's remaining figure — so its ledger and its order-derived figures name different months for an order raised 19:00–23:59:59 UTC on the last day of a UTC month. That gap predates this rule and is **deliberately not repaired**: legacy is the customer's own Karachi-based system and re-bucketing would break the reconciliation. `npm run audit:ke-budget-periods` measures it read-only; there is no `--commit`.
- **One-time add-on budgets carry a validity date, and the expiry is materialised onto the row** (`plans/OF-BUDGET-addon-validity.md`). A branch's money budget is one pool — `remaining = allocated + credited − spent − held` — and `budgets.amount_credited_cents` is read directly by the order hold, group orders, analytics, exports and the KE scripts, so an expired add-on is never subtracted at read time; it is withdrawn from the column. Every add-on that credits money (`PUT /api/v1/budgets`, `type: "addon"`, amount > 0) must carry `validUntil` (`YYYY-MM-DD`, resolved to 23:59:59 Asia/Karachi, today or later) and **is filed on the row for the month that date is in**, which must be one `addonPeriodsOpenAt` allows: the engine's **UTC** period or the administrator's Karachi month — the same month except 00:00–05:00 Karachi on the 1st, when a new-month date opens next month's row at the baseline rather than being refused. When that instant passes, `settleDueAddonsOnBudget` (`lib/server/budget-addon-expiry.ts`) withdraws `min(addonAmount, remaining)` — the **ceiling model**: base is spent first, spent and held are never touched, the check constraint always holds — records it on the `budget_addons` row (`expired_at`, `forfeited_cents`) and in `audit_logs` (`EXPIRE_BUDGET_ADDON`). The arithmetic is pure in `lib/budget-addon-expiry.ts`. **Every path that takes a hold settles under its own `FOR UPDATE` first** (orders POST, orders PATCH, group order creation); budget reads and writes settle too, and `POST /api/v1/budgets/cron/expire-addons` sweeps the rest behind `CRON_SECRET`. `lib/server/budget-addon-expiry.test.ts` pins that list — a new spending path goes on it. A row with `valid_until IS NULL` predates validity and is never settled. Refund credits (a refund of an unfulfilled order, or the part of one a short row could not debit, or one approved before `plans/OF-BUDGET-refund-ledger-debit.md`) land in the same column and are treated as non-expiring ceiling. A branch id on the budgets GET query string is fenced to the caller's tenant **before** `loadSingleBranchBudget`, because that load opens a period row when one is missing (`queriedBranchAccessError`, sharing `tenantFenceError` with the PUT).
- **A month's budget row opens lazily, at the branch baseline** (`plans/OF-BUDGET-open-current-month-on-budget-list.md`). No schedule writes it: the first order pre-flight, shop budget read, allocation, or Budgets list load of the month inserts it at `branches.baseline_budget_cents` — never at last month's allocation, so a figure written only into a month row (as the KE imports did) does not roll over. It is **not** the order's calendar month any more, and Head Office and Branch Admin no longer request before fulfilment. Super Admin has **no time limit**: a direct refund, approving a request (`POST /api/v1/admin/refunds`) and rejecting one (`PATCH /api/v1/admin/refunds/[id]`) check the order's state and capacity only. - **No order is fulfilled before it is delivered, whoever asks.** Every path to `FULFILLED` — the Super Admin `POST /api/v1/orders/[id]/fulfill`, a token hand-off from any of the five roles that may send one, a delivery that settles a waiting hand-off, and the 48-hour auto-fulfil sweep — requires `fulfillment_status = 'DELIVERED'` first. `fulfillApprovedOrder` (`lib/server/order-fulfillment.ts`) enforces it unconditionally in its single-winner claim (an undelivered order is `"conflict"`), and the fulfil route refuses earlier with 409 via `isOrderDelivered` (`lib/fulfillment-status.ts`). Delivery is recorded only through `progressOrderFulfillment` (`lib/server/order-fulfillment-progress.ts`), which Super Admin's `POST /api/v1/orders/[id]/fulfillment-status` and the warehouse's `POST /api/v1/warehouse/orders/[id]/progress` share; fulfilment never records it, and never overwrites `delivered_at`. A token handed over before delivery is remembered and settles the order when the delivery is recorded. Do not reintroduce a mode that fulfils and delivers in one step.
- **Group orders belong to the branch, not just to the requester**: a Group Order Portal submission is recorded as one ordinary `orders` row per branch, carrying a nullable `groupOrderId` back-reference. Every branch-scoped and organization-scoped read therefore already returns them — `BRANCH_ADMIN` and `HEAD_OFFICE` see and decide them with no special case, and **no query may ever add a `groupOrderId IS NULL` filter**. `ORDER_PORTAL` is the one role narrowed by creator, and it is narrowed to *own orders **or** group orders for its branch* (`lib/group-order-visibility.ts`), because a group order spends that branch's budget. - **A group requester may cancel a group order until it is approved — never after** (`plans/OF-GROUP-cancel-pending-group-orders.md`). `GROUP_ORDER_PORTAL` only, for group orders (`group_order_id` set) at a branch in its live assignment set — one branch order (`POST /api/v1/group-portal/branch-orders/[orderId]/cancel`, from its side panel in "My group orders") or every still-pending branch order of a submission it raised (`POST /api/v1/group-portal/orders/[groupOrderId]/cancel`; approved ones are kept and reported). - **The branch owns its orders — writes follow branch assignment, not authorship** (`lib/order-write-access.ts`). Either requester role may **edit** a pending order or **request a refund** on any order at a branch it is assigned to, whoever raised it: `ORDER_PORTAL` for its own branch (group orders included), `GROUP_ORDER_PORTAL` across its resolved assignment set (orders raised by branch staff included). The branch set is resolved server-side — `scope.branchId` for the single-branch role, `resolveScopedBranchIds()` for the group role — and **an empty set denies everything rather than widening to the tenant**. This reversed an earlier creator-equality rule, which was proving branch membership and personal accountability at once; only the first survives. The second moved to the trail: every cross-actor write records `onBehalfOfUserId` in its audit row and notifies the raiser through `notifyRaiserOfOrderWrite`, on the same transaction, so a rolled-back edit never announces itself. Deciding an order did **not** widen — approve, reject, fulfil and payment-status still refuse `GROUP_ORDER_PORTAL` — and neither did the invoice, which stays with the raiser. See `plans/OF-GROUP-branch-owns-order-writes.md`. **The fulfilment token hand-off is open to all five operational roles** (`HEAD_OFFICE`, `GROUP_USER`, `BRANCH_ADMIN`, `GROUP_ORDER_PORTAL`, `ORDER_PORTAL`) on any approved order already inside their read scope, regardless of who raised or approved it or the tenant's configured approver role. `canViewFulfillmentToken` (`lib/fulfillment-token-access.ts`) is now a role-and-status rule only; the scope is the caller's job — every surface that releases a token must first fence the order to the actor's tenant/branch/assignments, and `send-token-email` additionally holds `ORDER_PORTAL` to `canOrderPortalReadOrder` (own orders or group orders for its branch), so a guessed id cannot release a colleague's token.

- **The invoice ledger: a tax invoice is issued, numbered and dated when the order is marked In Process; a refund against it is a numbered credit note; neither ever changes** (`plans/OF-INVOICE-invoice-ledger.md`, issue point moved from delivery by `plans/OF-INVOICE-issue-at-processing.md` so the warehouse can print the invoice and send it with the goods). Tables `invoices`, `invoice_lines`, `credit_notes`, `credit_note_lines`, `credit_note_sequences` (migration `20261015120000`). **Issuing:** `issueTaxInvoice` (`lib/server/invoice-issuance.ts`) runs inside `progressOrderFulfillment`'s transaction — the only place a delivery stage moves — on every step `issuesTaxInvoiceOnStep` admits: `TAX_INVOICE_ISSUE_STAGE` (`IN_PROCESS`, `lib/invoice-policy.ts`) and every later one. It is idempotent, so the later steps find the invoice and do nothing, and an order that was already past In Process without one is issued it on its next step; an order in process or beyond without its invoice can only be one of those. The number comes from the organization's existing `invoice_sequences` series (`<ORGCODE>-APR-NNNNNN`, unchanged), drawn there so the series is gap-free; an order that already holds a number drawn at creation before the switch (a *reservation*, `reservedInvoiceNumber`) is issued with it. The date is the Karachi date of the step that issued it. Lines are the order lines less refunds approved before issue (`planIssuedInvoice`): a line leaves only when refunds took all its quantity, so goods delivered free are invoiced at zero (and an invoice with nothing left to pay is not unpaid — `orderStillOwes` / `orderStillOwesSql` in both the pending-invoice notice and the ordering block); an un-itemised legacy refund is shared across the lines to the paisa and each line re-split, never a header discount (`discount_cents` is 0 at supply). A refund line is priced by `refundLineAmountCents` (`lib/refund-amount.ts`): the refund that takes a line's last units gives back exactly what is left of its charge, and both approval routes re-check the price under the order lock (`refundDetailsStillPriced`). An organization with no usable code (`isInvoiceableTenantCode`) takes no order (`InvoiceCodeMissingError`, 409 at creation and at the issuing step), and its code locks only once a number has been drawn under it (`hasDrawnInvoiceNumber`: the sequence above 0, an invoice row, or an order holding a number) — never merely because orders exist. The number is also written into `orders.receipt_data.invoiceNumber`, which keeps every older reader of that field right. **Numbering at creation is off** (`INVOICE_ISSUE_POINT = "processing"` in `lib/invoice-policy.ts`, a code constant, not an env var); both creation paths go through `assignInvoiceNumberAtCreation`, and the edit paths keep a number only if the order already had one — never the TID. **Credit notes:** both refund-approval paths (`orders/[id]/refunds` for Super Admin, `admin/refunds`) call `issueCreditNoteForRefund` (`lib/server/credit-notes.ts`) in their transaction: against an invoice it issues `<ORGCODE>-CN-NNNNNN` from its own series and moves the invoice's `credited_*` and status. Each credited line's tax is taken from **what is left on that invoice line** (`planCreditNote` → `creditTaxFromLine`, fed each line's earlier credits under the invoice's `FOR UPDATE`), never by splitting the credit on its own — a per-note split credited 45.78 against 45.77 invoiced for PKR 100.01 × 3 refunded a unit at a time — so the credits on a line add up to its invoiced tax exactly, and the note that completes an invoice takes exactly the tax left on it; before In Process there is no invoice, so it only records `refunds.tax_refund_cents`, which every app refund now carries. `updateReceiptWithRefund` is gone: a refund never rewrites an invoice. **Immutability is enforced by triggers**: on `invoices` only `status` and `credited_*` may change, credits never go down, and `20261016120000` holds them to `credited_net + credited_tax = credited_total`, `credited_tax ≤ tax`, and (issued at supply) a status that matches the credited total; lines and credit notes refuse UPDATE and DELETE; `invoices.order_id` stops the order being deleted, and `admin/delete-order` refuses a delivered order with 409. Two narrow exceptions exist: the backfill's rollback, naming its own `backfill_batch` via `oneflowe.invoice_ledger_rollback_batch`, and test cleanup in a database whose name contains `test` (`tests/integration/helpers/invoice-ledger-cleanup.ts`; any suite that records a delivery must purge through it before deleting orders). **Documents:** an invoice issued at supply prints from its rows only (`invoiceDocumentForOrder` → `frozenInvoiceDocument`), on the preview, the download and the warehouse PDF — no live branch address, NTN, order status or fulfiller; legacy invoices keep printing from the snapshot as before, plus their credit notes. Credit notes download from `GET /api/v1/receipts/[orderId]/credit-notes/[creditNoteId]/download`, under the invoice's own access rule and price visibility. **Status:** once an invoice is issued, **its own `invoices.status` is the status** — `invoiceStatusSql` reads it first and `deriveInvoiceStatus` takes it as `ledgerStatus` — because a refund approved before delivery is taken off the invoice, not credited, and "supplied + refund > 0" would call that invoice partially credited. Before issue, `deriveInvoiceStatus` (`lib/invoice-status.ts`) and its SQL twin map an order to Not issued / Proforma available / Issued / Partially credited / Credited / Cancelled; an approved order not yet in process is a **PROFORMA INVOICE** (the title is never "Sales Tax Invoice"), and neither it nor an invoice whose goods are not yet delivered is an unpaid invoice — `lib/pending-invoice.ts` counts only Issued and Partially credited **and** supplied (`isOrderSupplied` / `orderSuppliedSql`), so the shop's notice still waits for delivery. The customer's STRN (`organizations.strn_number`, Create / Edit Organization, audited with the NTN as `UPDATE_ORGANIZATION_TAX_IDENTIFIERS`) is frozen onto each invoice at issue. A person who issued an invoice, a credit note or a delivery challan is deactivated, never hard-deleted, by `DELETE /api/v1/users/[id]`, whose hard delete runs its audit-log cleanup in the same transaction as the delete. **Rollout:** apply `20261014120000`, `20261015120000` and `20261016120000`, run `npm run backfill:invoice-ledger` (dry run, then `--commit` with its digest) to copy every invoice already supplied with its own number and printed date (`origin` LEGACY_*, no credit notes for old refunds), deploy, then run the backfill once more. `npm run report:invoice-number-register` explains every gap in a series (read-only). `lib/server/invoice-ledger-contract.test.ts` lists every writer of the ledger and every issuing hook; `tests/integration/invoice-ledger.test.ts` and `tests/integration/invoice-ledger-edge-cases.test.ts` carry the database behaviour (with `lib/invoice-ledger-edge-cases.test.ts` and `lib/refund-amount.test.ts`: every edge case they found is fixed, and each test says what used to happen), and `tests/e2e/invoice-ledger.spec.ts` the journey. The Playwright teardown switches on the test-cleanup exception, or no spec that delivers an order could tear down.

- **The database refuses a row whose branch or group belongs to another organization** (`plans/OF-DB-tenant-composite-foreign-keys.md`). Every operational table carrying `organization_id` with `branch_id` or `group_id` has a composite key `(branch_id, organization_id) -> branches (id, organization_id)` (or the group equivalent, plus `orders (group_order_id, organization_id) -> group_orders`), named `<table>_branch_org_fk` / `<table>_group_org_fk`, targeting `UNIQUE (id, organization_id)` on `branches`, `groups` and `group_orders`. A new table with both columns gets one too, and goes on `tests/integration/tenant-composite-foreign-keys.test.ts`, which compares `schema.ts` with the database. They are MATCH SIMPLE (a NULL in either column is not checked) and NO ACTION, beside the unchanged single-column keys — except `users.branch_id` and `branches.group_id`, which had no key before and are `ON DELETE SET NULL (column)` so a delete that worked still works. A branch or group therefore cannot move to another organization while anything references it. The append-only logs (`audit_logs`, `system_logs`, `group_audit_logs`, `notifications`, `email_outbox`, `product_price_history`) are deliberately not covered. A violation surfaces as Postgres 23503.
